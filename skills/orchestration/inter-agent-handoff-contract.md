# Skill Name: Inter-Agent Handoff Contract

## 🎯 Objective

Defines the minimal required schema and lifecycle for handing a bounded task (as produced by `orchestration/task-decomposition-and-routing.md`) from one agent to another, so the receiving agent gets complete context and the result can be tracked to a terminal state. `journeys/journey-orchestration-and-verification.md` already solved this for cross-**service** handoffs (trace-context propagation, contract testing); this skill is the agent-to-agent analog, scoped to a single structured object per call rather than a whole service API. Grounded in Google's own Agent2Agent (A2A) protocol, an open standard built specifically for this problem.

## 👤 Target Persona

Engineer building a multi-agent system where one agent's output must become another agent's input; the orchestrator agent itself, when it needs a concrete object shape rather than an ad hoc message.

## 📥 Inputs Required

- The bounded subtask specification from `orchestration/task-decomposition-and-routing.md` (objective, output format, tool guidance, boundaries).
- Sender and receiver agent identities, per `domains/agent-zero-trust-delegation.md`'s distinct-principal model.
- Any existing trace-context convention already in use (per `journeys/journey-orchestration-and-verification.md`), so agent-to-agent handoffs can be correlated into the same end-to-end trace as service-to-service calls.
- The scope/size limits already set by `orchestration/shared-context-and-state-ownership.md` for what a subagent is allowed to return.

## 📤 Expected Output

- A handoff object with mandatory fields: `task_id`, `sender`, `receiver`, `objective`, `boundaries`, `input_payload`, `output_contract`, `state`, `trace_id`.
- An explicit state machine governing every handoff, modeled on A2A's own `TaskState` enum.
- A rule separating this contract's WORK payload from the delegation grant's AUTHORIZATION envelope (`domains/agent-zero-trust-delegation.md`) — both required on a real call, neither substituting for the other.

## The Contract, Grounded in A2A

Google's Agent2Agent protocol was built to standardize exactly this handoff, and its data model maps directly onto what an inter-agent contract needs:

- **Task object** — "Unique identifier (e.g. UUID) for the task, generated by the server for a new task" (`id`), plus "The current status of a `Task`, including `state` and a `message`" (`status`), plus "A set of output artifacts for a `Task`" (`artifacts`). A handoff without a stable `task_id` cannot be tracked to completion or correlated in a trace.
- **TaskState lifecycle** — A2A names explicit states rather than a bare "done"/"not done": `SUBMITTED` ("task has been successfully submitted and acknowledged"), `WORKING` ("task is actively being processed by the agent"), `INPUT_REQUIRED` ("agent requires additional user input to proceed... an interrupted state"), and four **terminal** states — `COMPLETED`, `FAILED`, `CANCELED`, and `REJECTED` ("agent has decided to not perform the task"). A handoff that can only ever report "done" or silence loses the distinction between "still working," "blocked waiting on something," and "failed" — each of which requires a different next action from the orchestrator.
- **Message and Role** — "Identifies the sender of the message" (`role`) and "Parts is the container of the message content" (`parts`), with roles distinguishing client-to-server (`ROLE_USER`) from server-to-client (`ROLE_AGENT`) messages — i.e., the protocol distinguishes who is asking from who is answering, which a raw string payload does not.
- **Agent Card** — a discoverable, published description of what an agent can do and how to reach it (fetched via `/.well-known/agent-card`), so a caller doesn't need out-of-band knowledge of a specialist agent's capabilities before addressing it.

## 🤖 Core Prompt / Instructions

```text
You are constructing a handoff from one agent to another for a single
bounded subtask. Never hand off with a bare instruction string — build the
full contract object so the receiving agent has everything it needs and the
orchestrator can track the task to a terminal state.

Required fields, every handoff:
- task_id: a stable, unique identifier for this specific handoff (not the
  parent goal's ID) — generated once, referenced on every subsequent status
  update for this task.
- sender / receiver: the distinct agent identities involved, per
  domains/agent-zero-trust-delegation.md's principal model. Never let an
  agent's own reasoning stand in for an explicit identity field.
- objective / boundaries / output_contract: carried over verbatim from
  orchestration/task-decomposition-and-routing.md's subtask specification —
  do not re-summarize or loosen the boundary in translation.
- input_payload: the actual content the receiver needs, structured into
  typed parts (text / file / data) rather than one opaque blob, so the
  receiver doesn't have to guess what kind of content each part is.
- state: one of SUBMITTED, WORKING, INPUT_REQUIRED, COMPLETED, FAILED,
  CANCELED, REJECTED. Update it at every meaningful transition — a task
  silently stuck in WORKING with no timeout is a bug, not a valid steady
  state (see orchestration/agent-chain-failure-and-escalation.md for what
  happens when a task doesn't reach a terminal state in time).
- trace_id: the shared trace-context identifier from
  journeys/journey-orchestration-and-verification.md, so this agent-to-agent
  call is reconstructable in the same end-to-end trace as any service call
  the workflow also makes.

Rules:
- REJECTED is a legitimate terminal state, not a failure to hide — a
  receiving agent that determines it cannot or should not perform the task
  must say so explicitly via this state, not silently produce a low-quality
  attempt.
- This contract carries WORK (what to do, with what, returning what) — it
  is not an authorization mechanism. A receiving agent must still hold a
  valid delegation grant under domains/agent-zero-trust-delegation.md
  independently of receiving a well-formed handoff object. A complete
  handoff contract from an unauthorized sender is still a rejected call.
- INPUT_REQUIRED must name exactly what input is missing — an interrupted
  task with no stated blocker cannot be resolved by anyone downstream.

Now construct the handoff for:
Subtask: $BOUNDED_SUBTASK
Sender: $SENDER_AGENT
Receiver: $RECEIVER_AGENT
Trace context: $TRACE_ID
```

## ✅ Success Criteria / Quality Checklist

- [ ] Every handoff carries a stable `task_id`, distinct sender/receiver identities, and the boundaries/output_contract inherited unchanged from the decomposition step.
- [ ] Every handoff's `state` is one of the named lifecycle values, never a bare "done"/"not done" or silent absence of state.
- [ ] `INPUT_REQUIRED` and `REJECTED` are used when applicable, rather than the receiver silently guessing or silently under-delivering.
- [ ] The trace_id is present and matches the workflow's shared trace-context convention.
- [ ] The handoff contract (work) and the delegation grant (authorization) are checked as two separate requirements — neither is treated as satisfying the other.
